# 基于业务流程的用户视角功能测试方案

> 版本 0.1.0　|　沉淀自 mydatama v0.1.0 实机出片与缺陷拦截实践
> 配套资产：流程模板（templates/）、可执行程序（kit/）、范例（examples/mydatama/）

本方案回答九个问题：**怎么搭框架、怎么梳理流程、怎么模拟用户、用例长什么样、程序怎么写、
什么场景用、怎么落地、怎么评估好坏、怎么持续变好。**

---

## 一、测试框架设计

### 1.1 设计原则

1. **业务流程驱动，而非接口清单驱动**：测试单元是「一条用户价值链路」（如：上传数据→
   治理→建集→产品化→合规→挂牌），不是孤立的接口。
2. **数据靠 API 造，画面靠浏览器验**：HTTP 黑盒接口快速精确地制造前置状态，
   真实浏览器验证用户最终所见。两条通路分离，各自做最擅长的事。
3. **三层断言**：每层防不同类型的缺陷，缺一层就会漏：
   - 契约层（HTTP）：`code/status`、字段名、枚举值、状态机迁移是否合法；
   - 呈现层（DOM/视觉）：用户是否真的看得到数据、状态标签是否点亮；
   - 落库层（DB 只读）：审计列、约束、副作用是否真实持久化。
4. **正反双路径**：每条主链路至少一条快乐路径 + 一条「系统应正确拒绝」的反面路径
   （如密级倒挂应被拦截）。**预期失败也是 PASS**，放行才是缺陷。
5. **证据即输出**：每一步留存响应摘要、截图、耗时；报告只引用机器产出，不写主观推断。
6. **不修改被测业务代码**：测试程序是黑盒消费者；确需造特殊数据时，走显式开关
   （如 DEMO_TWEAK_DSN），默认关闭、仅限测试库。
7. **退出码即结论**：任一硬断言失败，进程退出码非零，可直接进 CI 门禁。

### 1.2 六层架构

```
┌─────────────────────────────────────────────────────────┐
│ 编排层   pytest（发现 *.flow.yaml / 失败传播退出码 / JUnit）│
├─────────────────────────────────────────────────────────┤
│ 流程层   业务流程 IR（YAML）：步骤/变量/断言/观察点/正反路径 │
├──────────────────────────────┬──────────────────────────┤
│ 造数通路      API 执行器       │ 验证通路      UI 执行器     │
│ requests / JWT / 轮询 / 重试   │ Playwright / 登录态注入     │
├──────────────────────────────┴──────────────────────────┤
│ 断言层   契约断言 · 状态机断言 · DOM 断言 · DB(只读)断言    │
├─────────────────────────────────────────────────────────┤
│ 证据层   响应留档 · 截图(含视觉基线) · result.json · 报告   │
├─────────────────────────────────────────────────────────┤
│ 环境层   docker compose · 健康检查 · 数据重置/幂等键        │
└─────────────────────────────────────────────────────────┘
```

### 1.3 流程 IR（中间表示）

一份 `.flow.yaml` 就是一条可执行业务流程，是人与机器的共同契约：

- `meta`：流程名、角色、业务价值、优先级；
- `env/reset/auth`：环境地址、可选重置命令（需 ALLOW_RESET 显式放行）、登录与登录态注入方式；
- `steps[]`：有序步骤，类型为 `api | poll | ui | sql`；
- 步骤间用 `capture` 传递变量（如上传后捕获 fileId 供后续路由使用）；
- 每步可带 `assert`（契约/DB）或 `dom`（呈现），可标 `expect_failure: true`。

YAML schema 的完整字段与注释见 [templates/flow.template.yaml](../templates/flow.template.yaml)。

### 1.4 与测试金字塔的关系

本方案是**塔尖的关键链路 E2E**：建议每系统 7~12 条主链路、单轮控制在 15 分钟内；
边界值、字段校验、异常组合下沉到 API 契约测试（或单测）；性能、安全另用专项。
不要把 E2E 套件写成第二个全量功能库——慢和脆是 E2E 失控的两大死因。

## 二、业务流程梳理方法

目标：把模糊的「系统能干什么」变成一份有序、有状态、有观察点的流程 IR。

### 2.1 五步梳理法

1. **画用户旅程（Who→Why→What）**：列出角色（admin/业务员/审计员…）与他们的核心目标。
   每个可独立交付价值的目标 = 一条候选主链路。
2. **拆业务能力与状态机**：标出链路经过的核心实体与状态迁移
   （如产品 `DRAFT→CONFIGURED→GENERATED→PASSED/BLOCKED→REGISTERED→LISTED`）。
   状态机是断言「系统行为合法」的黄金依据。
3. **定步骤（动作/前置/后置/观察点）**：每一步写清四要素：
   - 动作：调哪个 API 或打开哪个页面；
   - 前置状态：依赖上一步哪个变量（fileId、versionId…）；
   - 后置状态：状态机应迁移到哪、DB 应有什么副作用；
   - 观察点：用户在页面上应看到什么（数据行、状态标签、时间线、凭证号）。
4. **排数据与时序**：
   - **空态与满态分开拍**：「全零大屏」必须在造数开始前验证；「满态」在动线完成后验证；
   - 准备真实规模的样本数据（如 5 万行 CSV，而非 3 行玩具数据），性能与分页问题才会暴露；
   - 所有业务唯一键用「前缀+时间戳/随机码」生成，保证可重复执行（幂等复用或清理）。
5. **补反面路径与异常分支**：每条主链路问两个问题：
   - 系统应在什么输入下**拒绝**？（越权、密级倒挂、非法状态迁移、缺必填）
   - 外部依赖失败时如何表现？（上传坏文件、超时——用小样本模拟即可）

### 2.2 梳理产物

一次梳理的标准产物为：用户旅程表 → 主链路清单（含状态机图）→ 每条链路一份
`.flow.yaml` → 同步产出标准化测试用例（人读版，见第四章模板）。
建议评审时拉上产品/业务确认主链路清单，避免测偏。

## 三、用户视角模拟策略

### 3.1 「像用户」的四个真实

1. **真实入口**：用真实浏览器打开真实前端 URL，经过真实路由与渲染管线；
2. **真实身份**：用真实账号登录，按角色最小权限操作；越权类用例显式切换低权角色；
3. **真实数据**：业务规模、编码（GBK/中文列名）、文件形态尽量贴近生产；
4. **真实时序**：空态先于造数、轮询真实等待异步任务完成，不用写死的长 sleep 掩盖问题。

### 3.2 登录态注入：技术手段不改变用户视角

逐一点击登录表单既慢又脆。做法是：API 登录拿到令牌后，在浏览器每个页面加载前注入其
原生登录态（前端存在哪就注入哪）：

- localStorage 键（如 `mydatama_auth = {accessToken,...}`）→ `context.add_init_script()`；
- 或 Cookie（`context.add_cookies()`）。

之后浏览器直接访问业务路由，**页面渲染、路由守卫、接口鉴权全部是真实的**——
注入的只是凭证，不是页面结果。登出态/过期态另立用例验证。

### 3.3 三层观察法（站在用户眼睛 + 站在系统两侧）

| 层次 | 观察手段 | 能抓到的典型缺陷 |
|---|---|---|
| 契约层 | HTTP 状态码、响应 JSON 路径、枚举值 | 500、字段改名、状态机非法迁移、分页错误 |
| 呈现层 | DOM 文本/可见性/数量 + 截图视觉基线 | **接口 200 但页面空白**、状态标签不亮、错位 |
| 落库层 | 只读 SQL 查审计列/约束/关联 | NOT NULL 违约、漏写操作者、级联丢失 |

mydatama 缺陷 D（snake_case 致页面全空）正是呈现层的价值：契约层看 200 会误判通过。

### 3.4 多角色与权限视角

- 每条链路标注主角色；横切加一组权限用例矩阵（不必全组合）：
  未登录→401、已登录低权角色→403、管理员→200，**断言 HTTP 状态码而非仅 body**，
  并兼容空响应体，避免把「正确拒绝」误报为失败。
- 审计视角（如审计日志页）单独成链：谁在什么时间做了什么必须可查。

### 3.5 不 mock 的边界

- 不 mock 本系统内部服务（Java/Python/DB/前端之间全走真实链路），否则失去集成测试意义；
- 可替换外部不可控依赖（短信/支付/第三方模型）为桩，但桩必须返回与真实契约一致的数据；
- TTS/CDN 等与业务无关的外部依赖在测试中直接排除。

## 四、测试用例标准化模板

人读版用例（评审/手工执行/审计用）与机读版 `.flow.yaml`（自动化用）字段一一对应。
完整空模板：[templates/testcase.template.md](../templates/testcase.template.md)。

### 4.1 用例字段标准

| 字段 | 说明 |
|---|---|
| 用例 ID | `链路编号-序号`，如 `PROD-LIST-03`，全局唯一且稳定 |
| 所属链路/优先级 | 主链路名；P0 主路径 / P1 重要分支 / P2 异常 |
| 角色与视角 | 执行角色（admin/业务员…），注明多角色切换点 |
| 前置条件 | 环境状态、依赖变量、基线数据（账号/密级/模板预置） |
| 测试数据 | 文件、编码、规模、唯一键生成规则 |
| 操作步骤 | 编号步骤：动作 → 输入 → 路由/接口 |
| 三层预期 | ①契约（code/字段/枚举/状态迁移）②呈现（DOM/截图）③落库（SQL 只读） |
| 反面预期 | `expect_failure` 时期望的错误码/拦截位（如 403、BLOCKED） |
| 证据要求 | 必截的屏、必留的响应、查询语句 |
| 自动化映射 | 对应 `.flow.yaml` 中的 step id，保持双向可追溯 |
| 清理/幂等 | 复用键或清理动作，保证可重复执行 |

### 4.2 命名与粒度规范

- 一条 YAML = 一条用户价值链；一个 step = 一个不可再分的业务动作及其全部断言；
- step id 用业务语义（`upload_csv`、`compliance_should_block`），不用 `step1/step2`；
- 断言写在动作旁边，就近维护；跨步骤的状态机总断言放在链路末尾的 `final_assert`。

## 五、测试程序开发规范

### 5.1 目录与工程规范

- 测试程序与业务代码**分仓/分目录**，通过 HTTP 黑盒访问，禁止 import 业务内部模块；
- 统一从环境变量读取配置（BASE_URL、账号、DSN），随包提供 `.env.example`，严禁入库密钥；
- 产物统一落 `test-output/<流程>-<时间戳>/`，含 result.json、截图、响应留档、报告。

### 5.2 稳定性规范（防 flaky）

- **等待策略**：优先条件等待（任务轮询到 READY、等选择器出现、networkidle）；
  渲染宽限最多 1 次且 ≤2s；禁止用长 sleep 当同步手段；
- **重试边界**：仅对网络抖动/5xx/浏览器启动失败做有限退避（≤4 次）；
  **断言失败永不重试**——重试断言等于掩盖缺陷；
- **选择器优先级**：`data-testid` > 角色+文本 > 稳定语义 class > XPath/XPath 绝对路径；
- **数据隔离**：测试租户或唯一前缀；需要重置库时用 `reset` 段且必须设 ALLOW_RESET=1；
- **顺序解耦**：链路内变量显式 capture/引用；不同链路之间不得相互依赖执行顺序。

### 5.3 安全规范

- DB 通道默认只允许 SELECT/WITH；写操作仅限显式 `allow_write: true`（演示造数场景）；
- shell 重置命令默认禁用，必须双重显式放行（YAML + 环境变量）；
- 截图对敏感区域（手机号/证件号）用 `mask` 选择器打码后再归档；
- 反面流程不得依赖破坏真实安全策略的后门；需要特定数据态时用受限的测试专用开关。

### 5.4 断言与结果规范

- 统一响应信封约定可配置（如 `{code,message,data}`，code=0 成功），失败信息必须打印
  实际值与期望值、步骤 id、响应片段，便于定位；
- 反面用例以 HTTP 状态码为主断言，兼容空 body；预期拒绝归类 PASS；
- 结果结构化：每步记录 `id/类型/耗时/状态/断言明细/证据路径/错误`，主流程汇总并以
  pytest 退出码传播；报告字段必须来自 result.json，不允许无证据的结论。

### 5.5 扩展点

新增步骤类型（如 MQ 断言、WebSocket 等待）在 runner 中注册 handler 即可；
新增断言算子在 runner 的断言表中加函数；视觉基线默认关闭，环境变量开启。

## 六、适用场景界定

### 6.1 适用

- 多服务/全栈 Web 应用（前端 + API + DB + 异步任务），有 docker-compose 或等价起环境能力；
- 存在明确业务动线、状态机、多角色操作（审批、合规、订单、开户、上架等）；
- 发版回归、交付验收冒烟、上线前门禁；
- 需要向非技术干系人演示/留证「真实系统跑得通、页面看得到」。

### 6.2 不适用或需搭配专项

| 需求 | 应选手段 |
|---|---|
| 算法/计算正确性、字段边界值全组合 | 单元测试 / 属性测试 / API 参数化测试 |
| 高并发、吞吐、容量 | 性能压测（k6/JMeter） |
| 漏洞扫描、注入/越权深度挖掘 | 安全专项 |
| 复杂画布/游戏/视频剪辑等富交互 UI | 专用 UI 自动化 + 人工验收 |
| 无法独立部署的三方生产系统 | 契约录制/沙箱对账 |
| 视觉像素级还原设计稿 | 设计走查 + 专用视觉比对 |

### 6.3 准入条件 checklist

目标项目同时满足才建议引入：①可一条命令起干净环境；②有稳定测试账号；
③核心动线可文档化；④接受 10~15 分钟级的测试时长；⑤有 CI 或定时执行条件。

## 七、实施步骤（以两周落地一个项目为例）

1. **第 1 天｜环境与基线**：compose 一键起环境、健康检查通过；对齐测试账号与种子数据
   （账号/角色/ID 与文档一致，避免「用例对、数据错」的伪失败）。
2. **第 2~3 天｜梳理主链路**：与产品一起定 7~12 条主链路 + 状态机 + 正/反路径，过评审。
3. **第 4~6 天｜造数通路**：把每条链路的 API 动作写成 flow，跑通契约层断言与变量传递；
   异步任务用轮询；唯一键/幂等落地。
4. **第 7~9 天｜用户视角验证**：配置登录态注入；逐页补 DOM 断言与截图；
   空态/满态时序调整；关键表加只读 DB 断言。
5. **第 10 天｜反面与权限**：密级倒挂/越权/非法迁移/坏文件四类拒绝路径；401/403 矩阵。
6. **第 11 天｜试跑与去脆**：连跑 3 轮，统计 flaky；消除固定 sleep、强化选择器与数据隔离。
7. **第 12 天｜CI 接入**：nightly 或发版流水线：起环境→健康检查→pytest→归档证据→重置；
   失败以非零退出码阻断发布。
8. **第 13~14 天｜报告与移交**：出首份报告模板化结果；培训项目成员维护 flow；
   建立缺陷→断言的迭代台账（见第九章）。

## 八、质量评估指标

分两组：**被测系统的质量**与**测试套件自身的质量**，两组都要量化，否则套件会腐化失效。

### 8.1 系统质量指标（由套件产出）

| 指标 | 定义/目标 |
|---|---|
| 主链路通过率 | 通过的 P0 链路 / P0 总数；发版门禁要求 100% |
| 三层断言分布 | 契约/呈现/落库断言各跑了多少、失败在哪层，防止只写接口断言 |
| 状态机覆盖率 | 已覆盖的状态迁移 / 状态机全部迁移，含非法迁移拒绝用例 |
| 角色覆盖 | 已覆盖角色 × 关键操作矩阵的覆盖率 |
| 缺陷拦截数与分级 | 本轮拦截的 P0/P1/P2 缺陷数，附证据链接 |
| 空态/满态覆盖率 | 关键页面两类时序视图均有对应用例 |

### 8.2 套件质量指标（防腐化）

| 指标 | 定义/健康线 |
|---|---|
| flaky 率 | 重跑结果不一致的步骤比例；目标 <1%，>5% 必须停修 |
| 单轮时长 | 目标 ≤15 分钟；超时考虑拆并行或下沉低层测试 |
| 证据完整率 | 失败步骤 100% 有截图+响应留档；成功 P0 步骤有截图 |
| 逃逸缺陷率 | 上线后在已覆盖链路发现的缺陷 / 该链路总缺陷；逐季下降 |
| 误报率 | 「预期拒绝被报失败」「数据基线错位」类伪失败；目标 0 |
| 维护成本 | 每周因 UI 变更需要改的选择器数量；持续偏高说明缺 testid |
| 视觉基线差异 | VRT diff 超阈次数（基线漂移需人工确认后更新，禁止自动吞） |

报告模板见 [templates/report.template.md](../templates/report.template.md)，
所有数字必须来自 result.json 自动汇总。

## 九、迭代优化机制

### 9.1 缺陷 → 断言 闭环（核心机制）

每发现一个线上/测试缺陷，强制四步沉淀：

1. **复盘归因**：属于哪一层（契约/呈现/落库/环境/数据基线）？现有断言为何没拦住？
2. **先补红灯用例**：把缺陷动作写进对应 flow，确认在未修复版本上确实 FAIL；
3. **修复转绿**：业务修复后用例转 PASS，用例永久保留为回归资产；
4. **登记台账**：缺陷 id ↔ step id ↔ 提交 双向链接。
   mydatama 的 4 个缺陷已按此机制沉淀为范例（见 examples/mydatama/defect-lessons.md）。

### 9.2 套件级节奏

- **每次发版**：全量跑主链路，报告归档为版本交付物；
- **每周**：清 flaky、补 testid 工单、清理过期基线；
- **每季度**：重审主链路清单（业务变了就增删）、统计逃逸率与拦截 ROI，
  决定哪些 E2E 用例下沉为更快的契约测试，守住金字塔形态；
- **变更触发**：前端改页面 → 同步更新选择器；契约改字段 → 先改契约定义再改 flow。

### 9.3 成熟度分级（推广时的自检标尺）

- L1 可运行：环境一键起，主链路 API 跑通，有退出码；
- L2 用户视角：登录态注入 + DOM 断言 + 截图证据，空态/满态齐备；
- L3 可回归：3 轮无 flaky，CI 定时跑，报告自动归档；
- L4 可治理：缺陷闭环台账、逃逸率/flaky 等指标逐季向好，视觉基线纳入；
- L5 可复制：新项目按接入清单 ≤2 周达到 L3，模板零改动或仅加 handler。

本工具包的推广目标：**任何新应用项目 ≤2 周达到 L3。**
